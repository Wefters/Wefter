---
title: Environment Setup
description: What you need installed before building a Wefter app.
---

Before building a Wefter app, your machine needs four things in place: a
JavaScript runtime, a Java runtime the Android build tools can use, the
Android SDK itself, and something to actually run the app on. Here's what
each one does and why it's required, not just the version number to
install.

## Node.js and pnpm (can use npm)

The Wefter CLI, its plugin tooling, and your app's own frontend build (Vite,
or whatever bundler your framework uses) all run on Node. Node 18 or newer
is required because several packages in the toolchain use JavaScript
runtime features that don't exist in older versions.

pnpm is the package manager the CLI and its own packages are built around.
You can get by with npm for a plain app project, but pnpm is worth using if
you're building a plugin package that references other packages of your
own alongside it.

## JDK 17

This is easy to get wrong, because it's tempting to assume any recent Java
install will do. It won't. The Android Gradle Plugin, which is what
actually compiles your app's Kotlin and Java code, requires JDK 17
specifically as of its current version. JDK 8 or JDK 11, which used to be
the standard recommendation for Android work, will fail partway through a
build with an error that doesn't always point clearly back at the JDK
version as the cause.

Once installed, set `JAVA_HOME` to point at your JDK 17 install. On macOS
and Linux this usually means adding a line like `export
JAVA_HOME=/path/to/jdk-17` to your shell profile. On Windows it's an
environment variable set through System Properties. Confirm it worked with
`java -version` in a fresh terminal, since a shell session you already had
open won't pick up a change you just made.

## The Android SDK

The SDK is the actual set of tools and platform files Gradle needs to
compile and package an Android app: the compiler toolchain for a given API
level, the resource packager, and `adb`, the command-line tool used to
install and debug apps on a connected device or emulator.

Two environment variables matter here, `ANDROID_HOME` and its older alias
`ANDROID_SDK_ROOT`, both of which should point at wherever you installed
the SDK. If you installed Android Studio, the SDK usually lives under
something like `~/Android/Sdk` on Linux and macOS, or
`%LOCALAPPDATA%\Android\Sdk` on Windows, and Studio sets this for you
automatically. If you're working from the command-line SDK tools alone,
without the full Studio install, you'll need to set it yourself.

`platform-tools`, the folder inside the SDK that contains `adb`, needs to
be on your system `PATH`. Without this, `wefter run` can build an APK just
fine but will fail the moment it tries to install that APK onto a device,
since it can't find `adb` to do it with.

## A device or emulator

You need somewhere to actually run the app. Two options:

**A physical Android device**, connected by USB, with Developer Options and
USB debugging turned on. Developer Options is hidden by default. You unlock
it by opening Settings, finding the Build Number entry under About Phone,
and tapping it seven times. Once it's visible, USB debugging is a toggle
inside the new Developer Options menu.

**An Android Virtual Device**, or AVD, which is Android's own emulator. If
you've already created one, you can start it directly from the command
line with `emulator -avd <name>`, without needing Android Studio open at
all.

## Verify with `wefter doctor`

You don't need to check any of the above by hand. `wefter doctor` checks
all of it for you:

```bash
wefter doctor
```

It runs through, in order: your Node.js version, whether `ANDROID_HOME` is
set, whether `adb` is reachable on your `PATH`, your JDK version, and
whether a device or emulator is currently connected. Every failing check
prints a concrete fix rather than just a pass or fail, so you're never left
guessing what to do next.

Before a release build, run it with `--release-readiness` added, which
extends the same checks to cover signing configuration and anything else
that would block a real release:

```bash
wefter doctor --release-readiness
```
