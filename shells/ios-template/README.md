# shells/ios-template

The iOS counterpart to `shells/android-template` — see `IOS_IMPLEMENTATION_GUIDE.md` at the
repo root for the full design rationale. This file covers what's specific to actually opening
and building this template, since none of that could be exercised on the machine that wrote it
(see the guide's Section 0 — this whole template was authored on Linux, with no Xcode
available to compile or verify it).

## Before you build this for the first time

1. **Requires Xcode 16 or later.** `project.pbxproj` uses `PBXFileSystemSynchronizedRootGroup`
   for the `WefterBridge/Plugins/` folder (`objectVersion = 77`) — the mechanism that lets
   `copy-native-source-ios.ts` drop plugin `.swift` files straight onto disk with zero
   `project.pbxproj` edits, mirroring how any `.kt` file placed under Android's `src/main/java`
   is picked up by Gradle automatically with no `build.gradle.kts` change. Older Xcode cannot
   open a project in this format.
2. **Open it in Xcode before running `xcodebuild` from the CLI.** `project.pbxproj` was
   hand-authored (see below) — internally consistent by construction (every object ID was
   generated and cross-checked programmatically, see the generation notes in this repo's
   history), but never actually opened in Xcode. The very first thing to do on a Mac is open
   `WefterBridge.xcodeproj`, let Xcode index it, and fix anything it flags before wiring up
   `wefter build ios` / `wefter run ios` against it.
3. **Wire up the local `NativeDependencies` package by hand, once.** `NativeDependencies/`
   is a real, valid local Swift package (see its `Package.swift`) whose dependency list gets
   regenerated by `generate-native-dependencies-package.ts` on every sync — but the _reference_
   from the app target to this local package was deliberately **not** added to
   `project.pbxproj` here. Hand-authoring a local Swift package reference
   (`XCLocalSwiftPackageReference` + `XCSwiftPackageProductDependency`) blind, with no way to
   verify it, was judged a worse risk than a one-time manual step: in Xcode, use _File → Add
   Package Dependencies → Add Local..._, pick the `NativeDependencies` folder, and add it to
   the `WefterBridge` target. Until a plugin actually declares an
   `nativeDependencies.ios.spm` entry this has no visible effect either way.
4. **No demo plugin ships in this template.** `WefterBridge/Plugins/` is empty and
   `GeneratedRegistry.swift` registers nothing until `wefter sync` runs against a real project
   with at least one plugin declared. Build the template as-is first to confirm the bare bridge
   compiles before adding a plugin into the mix.

## What's intentionally not here yet

- **No XCTest target.** Android ships `BridgeDispatcherTest.kt`; this template has no Swift
  equivalent yet. Adding one is a normal Xcode operation (_File → New → Target → Unit Testing
  Bundle_) — deliberately left for whoever first opens this in Xcode, rather than hand-authored
  blind alongside everything else in `project.pbxproj`.
- **No physical-device signing set up.** `CODE_SIGN_STYLE = Automatic` with no team ID —
  fine for Simulator builds, needs a real Apple Developer team selected in Xcode (or
  `WEFTER_IOS_TEAM_ID` wired through, see `native/signing-ios.ts`) before it'll run on hardware.

## Mapping to `shells/android-template`

See `IOS_IMPLEMENTATION_GUIDE.md`'s Section 2 parity table for the full mapping. The short
version: `Config/*.xcconfig` is where the CLI writes what Gradle's `build.gradle.kts` marker
blocks hold on Android (bundle ID/app name per environment); `BuildConfig.swift` holds what
Android gets for free from Gradle's generated `BuildConfig` class (`DEV_SERVER_URL`, splash
timing) — see that file's own header comment for why it isn't in an `.xcconfig` instead.
